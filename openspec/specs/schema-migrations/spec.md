# schema-migrations Specification

## Purpose
Defines how the parcial's domain schema is versioned and materialized in PostgreSQL: the four chained
Alembic migrations, the third one autogenerated and hand-corrected, the fourth one hand-written with the
append-only trigger on `movimiento_stock`, the round-trip on an empty database, and the absence of
differences in `alembic check`.

## Requirements

### Requirement: Full schema from upgrade head on empty DB

The system SHALL create the complete parcial schema (all inherited TP tables plus `usuario`,
`asignacion_rol`, `intento_acceso`, `evento_seguridad`, `movimiento_stock`, `cliente.usuario_id`,
`libro.borrado_en` and the two partial unique indexes) by running `alembic upgrade head` on an empty
PostgreSQL 16 database, without any `create_all` call.

#### Scenario: empty database becomes complete schema

- **WHEN** `alembic upgrade head` runs against an empty database
- **THEN** all the tables, columns, constraints and indexes listed above exist and the command exits
  successfully

### Requirement: Migration 0003 adds the eight pieces

Migration `0003` SHALL add the four access tables (`usuario`, `asignacion_rol`, `intento_acceso`,
`evento_seguridad`), `movimiento_stock`, the `cliente.usuario_id` column, the `libro.borrado_en` column,
and the two partial unique indexes (`asignacion_rol` on (usuario_id, rol) WHERE revocada_en IS NULL and
`libro` on (isbn) WHERE borrado_en IS NULL). It SHALL remove the common `UNIQUE(isbn)` constraint on
`libro`.

#### Scenario: eight pieces present after 0003

- **WHEN** the schema is upgraded to revision `0003`
- **THEN** the five new tables, the two new columns, and the two partial unique indexes exist, and the
  common `UNIQUE(isbn)` constraint is absent

### Requirement: Migration 0003 records hand corrections

Migration `0003` SHALL carry a header comment stating that it was read before applying and listing what
was corrected by hand: inferred types, the `postgresql_where` of the two partial indexes, `borrado_en` as
`timestamptz`, and the indexes of the new foreign keys (and the drop of the common `UNIQUE(isbn)`).

#### Scenario: hand-correction comment present

- **WHEN** the file of migration `0003` is inspected
- **THEN** it contains a comment declaring that it was read before applying and enumerating the
  corrections above

### Requirement: Migration 0004 installs append-only trigger

Migration `0004` SHALL create a PostgreSQL function and a trigger that reject any `UPDATE` or `DELETE` on
`movimiento_stock`, and its `downgrade` SHALL drop both the trigger and the function.

#### Scenario: update and delete rejected

- **WHEN** an `UPDATE` or `DELETE` is attempted on `movimiento_stock` after `upgrade head`
- **THEN** the statement fails and no row is modified or removed

#### Scenario: downgrade removes trigger and function

- **WHEN** `alembic downgrade` past `0004` runs
- **THEN** the trigger and the function no longer exist

### Requirement: Round trip on empty database

Running `alembic upgrade head`, then `alembic downgrade base`, then `alembic upgrade head` against an
empty database SHALL succeed in all three steps.

#### Scenario: three steps succeed

- **WHEN** the three commands run in sequence on an empty database
- **THEN** each exits successfully

### Requirement: No pending differences after upgrade

After `alembic upgrade head`, running `alembic check` SHALL report no differences between the models and
the database schema.

#### Scenario: alembic check clean

- **WHEN** `alembic check` runs after `upgrade head`
- **THEN** it reports no operations pending

### Requirement: No create_all anywhere

The codebase SHALL contain no call to `create_all` in any Python file.

#### Scenario: grep empty

- **WHEN** the repository is searched for `create_all`
- **THEN** no matches are found

### Requirement: env.py imports all domain models

`migrations/env.py` SHALL import every domain model module, including `app.modules.usuarios.models`, so
that `autogenerate` sees all tables.

#### Scenario: usuarios models imported

- **WHEN** `migrations/env.py` is inspected
- **THEN** it contains an import of `app.modules.usuarios.models`

### Requirement: Correct types in migrations

The migrations SHALL define money columns as `NUMERIC` and the new date columns (`borrado_en`,
`desde`, `vence_en`, `revocada_en`, `cuando` of `intento_acceso`/`evento_seguridad`/`movimiento_stock`) as
`timestamptz`. Every new foreign key column SHALL have its own index.

#### Scenario: types and indexes correct

- **WHEN** the generated columns and indexes are inspected
- **THEN** money is NUMERIC, new dates are timestamptz, and each new FK has an index

### Requirement: Exactly five chained migrations

The project SHALL contain exactly five migration versions, chained so that `0001` has no down
revision, each subsequent one revises the previous, and `0005` is the head. Revision `0005` SHALL be a
new file: migrations `0001`, `0002`, `0003` and `0004` MUST NOT be edited. Its filename SHALL carry the
ordinal `0005` and a descriptive suffix, consistent with the numeric convention used by `0001`/`0002`.

#### Scenario: five versions in order

- **WHEN** `alembic history` is inspected
- **THEN** it lists `0001`, `0002`, `0003`, `0004`, `0005` in order with `0005` as head

#### Scenario: applied migrations are not rewritten

- **WHEN** the files of migrations `0001`…`0004` are compared with the revision history of the
  repository
- **THEN** their content is unchanged; the fix lives only in `0005`

### Requirement: Server defaults evaluate now() at operation time

Las columnas `asignacion_rol.desde`, `intento_acceso.cuando`, `evento_seguridad.cuando`,
`movimiento_stock.cuando` y `venta.fecha` SHALL tener `DEFAULT now()` evaluado por PostgreSQL en el
momento de cada inserción, no un literal `timestamp with time zone` congelado. `pg_get_expr(adbin,
adrelid)` para las cinco columnas SHALL devolver `now()`. Los cinco modelos SQLModel SHALL declarar
`server_default=text("now()")` para que `alembic check` siga sin diferencias.

#### Scenario: pg_get_expr devuelve now()

- **WHEN** se consulta `pg_get_expr(adbin, adrelid)` para las cinco columnas
- **THEN** las cinco devuelven `now()` y ninguna devuelve un literal con fecha

#### Scenario: dos inserciones en transacciones distintas difieren

- **WHEN** se insertan dos filas de `evento_seguridad` en transacciones separadas con al menos 1 ms de
  diferencia
- **THEN** sus `cuando` no son idénticos y ambos están próximos a la hora real de la operación

#### Scenario: alembic check limpio

- **WHEN** se ejecuta `alembic check` después de `alembic upgrade head`
- **THEN** no reporta operaciones nuevas

### Requirement: Migration 0005 is reversible and preserves history

La migración `0005` SHALL usar `ALTER TABLE … ALTER COLUMN … SET DEFAULT now()` en `upgrade`. Su
`downgrade` SHALL restaurar la forma histórica de `0003` (cadena `'now()'`, que PostgreSQL congela al
aplicar) y SHALL declarar en la cabecera que esa forma reproduce el defecto heredado a propósito, para
que el descenso sea reversible. **No** SHALL reescribirse ninguna fila histórica.

#### Scenario: los datos históricos no se reescriben

- **WHEN** se ejecuta la migración `0005` sobre una base con filas previas
- **THEN** ninguna fila existente de `movimiento_stock`, `evento_seguridad`, `intento_acceso`,
  `asignacion_rol` o `venta` cambia de valor

#### Scenario: round trip reversible

- **WHEN** se ejecuta `alembic upgrade head`, `alembic downgrade base` y `alembic upgrade head`
- **THEN** los tres pasos terminan sin error y el head vuelve a dejar `now()` en las cinco columnas
