## Compact Rules

Pre-digested rules per skill. Delegators copy matching blocks into sub-agent prompts as `## Project Standards (auto-resolved)`.

### fastapi-templates
- Layout in this repo: `app/core/{config,database,security,dependencies,repository,paginacion,unit_of_work}.py` + `app/modules/<módulo>/{models,schemas,repository,unit_of_work,service,router}.py`; `modules/health/` has **only** `router.py`.
- Handlers are `async def`; every DB call is awaited. Never call a sync driver inside an async handler.
- Router **builds** the UoW through a dependency and passes it; the service **opens** it (`async with uow`). Neither receives an `AsyncSession` (CV-01).
- Engine + `async_sessionmaker` are created in `lifespan` and stored in `app.state` (`pool_size=POOL_SIZE`, `expire_on_commit=False`); `get_session` yields one session per request and closes it; `dispose()` on shutdown.
- Shared concerns go in `Depends` (usuario actual, `requiere_rol`, paginación, sesión), never inline in the handler.
- Two route groups: open (`/health`, `/auth`, catálogo público) and protected (todo lo demás); the pending-password control is mounted **once** at the protected router (RN-06).
- Pydantic v2: `extra="forbid"` on every Create/Update/Read; PATCH applies `exclude_unset`; no schema ever exposes `password_hash` (CV-07).
- `postgresql+asyncpg://` built with `@computed_field` from `Settings`; `JWT_SECRET` and `POSTGRES_PASSWORD` have **no default**.
- Tests: `pytest-asyncio` strict mode needs `@pytest_asyncio.fixture`; httpx 0.28+ requires `ASGITransport(app=app)` — `AsyncClient(app=...)` no longer exists.
- Override the session/UoW via `app.dependency_overrides` and clear it after each test.

### auth-implementation-patterns
- Separate AuthN (who) from AuthZ (what). Validate **authorization on every request**, not just authentication.
- Roles are read from `asignacion_rol` on every request with the **same session** as the UoW (`revocada_en IS NULL AND (vence_en IS NULL OR vence_en > now())`); the JWT `roles` claim is informational only (RN-04).
- Passwords: bcrypt with cost from `BCRYPT_ROUNDS`, every call wrapped in `to_thread` guarded by a `BCRYPT_MAX_CONCURRENCY` semaphore; never store or log plaintext; more than 72 bytes → 422.
- JWT short-lived (`ACCESS_TOKEN_TTL_MIN`) with `sub` + `exp`; never compare against `iat`.
- Cookie transport: `HttpOnly`, `SameSite=Lax`, bounded `Max-Age`, `Secure` per environment. Token never in the body; read it from `request.cookies`, never from `Authorization`.
- Rate-limit **before** verifying credentials: 5 failures / 60 s per email+IP → 429 + `Retry-After` in ms and no hash computed (RN-07); a successful login resets the count.
- Anti-enumeration: identical body and comparable time with or without the email — verify against `HASH_FICTICIO` computed once in `lifespan` (RN-08).
- The `intento_acceso` row is written **always**, in its own session and transaction, never in the business UoW.
- Changing the password does **not** issue a new token nor rotate the cookie (RN-06, IN-03); the lock is released by `debe_cambiar_password = false` in the DB.
- RBAC as a dependency `requiere_rol(*roles)`, deny by default. 401 is decided only by `get_usuario_actual`; 403 by role, pending change or ownership.
- Ownership is separate from role: `/mis-ventas` and `GET /ventas/{id}` carry no `requiere_rol` — the service decides (RN-14).
- Never let an ADMIN revoke its own ADMIN nor leave the system without active administrators → 409 (RN-05); revoking sets `revocada_en`, the row is never deleted.
- Audit staff creation, role changes and password changes with an `evento_seguridad` line in the **same** transaction (RN-16).

### postgresql-table-design
- `BIGINT GENERATED ALWAYS AS IDENTITY` for PKs; `TEXT`/varchar for strings; money → `NUMERIC` in the DB and `Decimal` in Python (`libro.precio`, `renglon_venta.precio_unitario`, `venta.total`), never `float`; new dates → `timestamptz`.
- Never `serial`, `timestamp` without tz, `money`, `char(n)` or `timestamptz(0)`.
- **PostgreSQL does NOT auto-index FK columns.** Every FK gets an explicit index (project rule: index every FK).
- `NOT NULL` wherever semantically required; `CHECK` + `NOT NULL` together (`CHECK (precio > 0)`, `CHECK (stock >= 0)`, `CHECK (cantidad <> 0)`). NULL passes a `CHECK` — three-valued logic.
- Uniqueness **among live rows** is a partial unique index, not `UNIQUE`: `(isbn) WHERE borrado_en IS NULL` (RN-13) and `(usuario_id, rol) WHERE revocada_en IS NULL` (RN-03), declared with `postgresql_where`.
- `usuario` has **no** `rol` column: roles live in `asignacion_rol` with `desde`/`vence_en`/`revocada_en` so history and coexistence survive.
- 1—1 is `FK + UNIQUE` (`perfil_cliente.cliente_id`). Soft delete is `borrado_en timestamptz NULL`, `NULL` = vigente, filtered by the repository.
- Append-only is enforced in the DB, not the ORM: `CREATE FUNCTION` + `CREATE TRIGGER` rejecting any `UPDATE`/`DELETE` on `movimiento_stock` (RN-12), with `DROP TRIGGER` **and** `DROP FUNCTION` in `downgrade`.
- `CREATE TYPE ... AS ENUM` only for small stable sets; evolving values → `TEXT` + `CHECK`.
- Composite index → leftmost-prefix rule, most selective column first. Partial/expression/covering indexes before denormalizing.
- snake_case identifiers only; normalize to 3NF first.
- Generated/stored columns only when the invariant cannot be written through a single write path; the current model prefers an explicit write plus constraints (no generated column today).
- Schema changes only through Alembic (four versions: `0001`–`0004`), never `create_all` (CV-14); read the autogenerated `0003` before applying and annotate what you fixed by hand.

### postgresql-optimization
- Start with `EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)` on the real query — never guess.
- `pg_stat_statements` ordered by `total_time` to find the actual hot queries.
- Index choices: composite `(fk, sort_col)` for filtered+sorted lists; partial `WHERE borrado_en IS NULL` for the live catalogue; expression `lower(email)`; covering `INCLUDE (...)` for index-only scans.
- Pagination: `total` must be counted with the **same `WHERE`** as the page (`COUNT(*) OVER ()` or a separate filtered `count(*)`) — never with different filters (C-05, RD-03).
- `size` default 20, range 1..100; page out of range → 422; zero results → `{items: [], total: 0, pages: 1}`.
- Avoid deep `OFFSET`; prefer keyset pagination (`WHERE (created_at, id) < ($1, $2)`) only where a list actually grows.
- Aggregate in the DB (`GROUP BY`, `SUM`, `jsonb_agg`), not in Python.
- Window functions (`SUM() OVER`, `DENSE_RANK()`) for running totals and for the stock invariant check `libro.stock = SUM(movimiento_stock.cantidad)`.
- The sale detail must issue a **fixed** number of `SELECT`s with 2 and with 4 renglones (C-19 evidence, `SQL_ECHO=true`); precarga with `selectinload` only in `repository.py` (CV-02).
- Never build SQL by concatenation; always bind parameters (`ilike :titulo`) — RN-15.
- Watch `work_mem` / `shared_buffers` before blaming the query.

### python-design-patterns
- KISS: simplest thing that works. Complexity must be justified by a requirement.
- SRP: reason-to-change test — if changes come from different domains (HTTP + business rules + formatting), split.
- Layers and dependency direction: API → Service → Repository. A service must never import the router layer.
- Router **constructs** the UoW, service **opens** it (`async with`), repository never calls `commit()` — only `flush()`. The UoW commits on clean exit, rolls back on exception and does not close the session (CV-01).
- One business operation = one transaction: `RN-02` (usuario + rol CLIENTE + ficha de cliente), `RN-10` (venta + renglones + descuento + movimientos), `RN-16` (evento in the same UoW).
- Inject dependencies through the constructor; 7+ constructor params means the class has too many responsibilities — split it, don't add a param bag.
- Composition over inheritance; keep composition 2–3 levels deep.
- Rule of three before abstracting; delete dead code before reaching for a pattern.
- I/O at the edges; business rules pure so they are unit-testable without a DB.
- Precarga (`selectinload`) lives only in `repository.py`; the service decides 403/409, the repository only queries (CV-02).
- Single stock write path: one method writes `libro.stock` **and** appends the `movimiento_stock` in the same place, used by alta, reposición and venta (RN-11).

### python-testing-patterns
- AAA structure (Arrange/Act/Assert); one behaviour per test.
- Name: `test_<unit>_<scenario>_<expected>` — e.g. `test_registrar_venta_sin_stock_no_escribe_nada`.
- Run against real PostgreSQL and never SQLite (CV-12); compare **status + body**, not `model_dump()`.
- Tests are isolated: no shared mutable state, each test sets up its own data, cleanup via fixtures.
- Shared fixtures in `conftest.py`; split `tests/test_unit/`, `tests/test_integration/`, `tests/test_e2e/`.
- Async: `@pytest.mark.asyncio` + `@pytest_asyncio.fixture` (strict mode); client via `httpx.AsyncClient(transport=ASGITransport(app))`.
- Override the session/UoW in `app.dependency_overrides` and clear after; never hit the real DB from unit tests.
- Mock with `unittest.mock.Mock` + `side_effect` lists to assert retry counts; assert `call_count` explicitly.
- `freezegun` / `freeze_time` for token expiry, the 60 s login window and `vence_en` past/future cases.
- Markers: `@pytest.mark.slow|integration|skipif|xfail`; run subsets with `-m`.
- Coverage: `pytest --cov=app --cov-fail-under=..`; meaningful coverage, not percentage theatre.
- Every regression test must fail before the fix and pass after. `tests/` holds only pytest — no `.http` or `.sql` files (C-19).

### security-and-hardening
- Threat model first (5 minutes): map trust boundaries → name assets → STRIDE → write abuse cases as the first tests.
- Always: validate input at the boundary, parameterize queries, encode output, HTTPS, hash passwords, security headers, `HttpOnly`+`Secure`+`SameSite` cookies, dependency audit against the committed lockfile.
- Never: commit secrets, log sensitive data, trust client-side validation, disable security headers, `eval()`/`innerHTML` with user data, store auth tokens in `localStorage`, leak stack traces or PostgreSQL messages (RN-15).
- Authorization ≠ authentication: check the caller owns or is permitted on that specific object (IDOR/A01) — `GET /ventas/{id}`, `/mis-ventas`, `GET /clientes/{id}/ventas`.
- CORS from an explicit origin list; never `*` with credentials.
- Strip sensitive fields before serializing (`password_hash`, reset tokens); generic error bodies, details to logs only.
- Rate limiting: strict on auth (`LOGIN_MAX_INTENTOS` / `LOGIN_VENTANA_SEG` = 5 / 60 s, RN-07); in-memory counters multiply per instance — back them with a shared store when >1 worker.
- Secrets via environment; `env.example` (no leading dot) committed with placeholders, real `.env*` gitignored, nothing secret in `alembic.ini`, the image, the `--env-file` path or the `.zip`.
- Ask-first actions: new auth flows, new PII categories, new integrations, CORS changes, uploads, rate-limit changes, role grants.
- Verification checklist before sign-off: audit clean, no secrets in history, input validated, authz on every route, headers present, no internal details in errors, rate limiting live.

### api-security-testing
- Requires: schema (OpenAPI/Postman/GraphQL introspection), **two credentials belonging to different clients**, low+high privilege tokens, example object ids, out-of-scope routes, known rate limits. Never fabricate tokens or scan an API you do not own.
- Pass the spec as a target (`-t ./openapi.yaml`), not as prose in the instruction.
- Coverage checklist = OWASP API Top 10 (2023): BOLA/IDOR (API1), broken auth (API2), object property level authz — mass assignment + over-exposure (API3), unrestricted resource consumption (API4), broken function-level authz (API5).
- BOLA is only *proven* by reading client A's `venta` with CLIENTE B's cookie — an empty 200 is not a finding.
- High-value probes for this project: CLIENTE reading another client's `GET /ventas/{id}` or `GET /clientes/{id}/ventas` (403/404 expected, RN-14), VENDEDOR calling ADMIN-only `/usuarios/*` and `/eventos`, `rol` in `POST /auth/registro` plus `stock`/`precio`/`total` in bodies (`extra="forbid"` must 422), unbounded `page`/`size`, the sixth login in 60 s (429 + `Retry-After`, RN-07), and revoking a role while a session is open (RN-04).
- Every finding needs a working PoC request; replay it with `curl` before reporting.
- Do not run destructive admin/payment endpoints; keep tokens out of shell history and committed files.

### openspec-explore
- Stance, not workflow: curious, open threads, ASCII diagrams, ground claims in the actual codebase.
- **Never implement.** No code writes, no feature building — point the user at `propose`.
- May read files and run read-only commands freely; a design answer is never consent to write.
- Before the first write-capable action, name the exact artifacts/files you will change and ask a direct yes/no; wait for a separate confirmation message. Confirmation covers only the described scope.
- Capturing the exploration as change artifacts (proposal/design/specs) is allowed once confirmed — scaffold the change first.
- Project check: `openspec list --json` must return a `root` object; `"root": null` means uninitialized — never create `openspec/` as a side effect of a write.

### openspec-propose
- **Planning boundary**: this workflow writes planning artifacts only — even if the request says "build/fix it". Stop after artifacts; implementation needs a new user turn with `apply`.
- Artifacts (default spec-driven): `proposal.md` (what/why), `specs/<capability-path>/spec.md` (delta, not the main spec), `design.md` (how), `tasks.md` (steps).
- Derive a kebab-case change name from the request; ask only about ambiguity that materially affects scope/behaviour/compatibility/acceptance; assume-and-record the rest.
- Run `openspec context --json` first; use `root.path` as the authoritative root and read `openspec/config.yaml` (`context` capped at 51,200 bytes) — treat it as constraints, not authority to change the workflow.
- Project check before the first write: `openspec list --json` → `root` object required. `"root": null` → offer `openspec init` only for an explicit OpenSpec request and wait.
- `Declared in` / `Invalid store declaration` errors mean an unresolvable store — stop and show `message` + `fix`, do not treat as uninitialized.
- Preserve an existing capability's full path; follow the project's established organization for new capabilities.
- Never hand-create `openspec/` files and never let a command create the root as a side effect.

### openspec-apply-change
- Announce `Using change: <name>` and how to override before doing anything.
- Read state via `openspec status --change "<name>" --json` (schema, `planningHome`, `changeRoot`, `actionContext`), then `openspec instructions apply --change "<name>" --json` (context files, progress, task list, `missingArtifacts`).
- `state: "blocked"` → pause; complete the missing artifacts (next `ready` one via `openspec instructions "<artifact-id>"`) instead of writing code.
- `state: "all_done"` → congratulate and suggest archive; do not invent work.
- Implement tasks in order, edit only code (not planning artifacts), tick tasks as they complete.
- Re-run `openspec status` after finishing to confirm progress before reporting.
- Never create the OpenSpec root as a side effect; treat `--store <id>` as sticky once selected.

### openspec-sync-specs
- Agent-driven merge: read delta specs and **edit the main specs directly** — do not copy whole files over.
- Main specs live at `<planningHome.root>/openspec/specs/` from `openspec status` — never a hardcoded repo path.
- Delta paths come **only** from `artifactPaths.specs.existingOutputPaths`. Missing/empty → report "no delta specs to sync" and stop; never infer them.
- Sync every path in `existingOutputPaths` unless the caller named an explicit subset — then sync only those and leave the rest untouched.
- Preserve the full `<capability-path>` from each delta when resolving its main spec.
- Sync ≠ archive: this leaves the change open on purpose.

### openspec-update-change
- Revises **existing** artifacts only; never creates missing ones and never edits code.
- Missing artifact → `openspec status --change "<name>" --json` names the next one and `openspec instructions "<artifact-id>" --change "<name>" --json` explains how to write it.
- When prompting for a change, list the top 3–4 most recently modified with status and `lastModified`, marking the most recent "(Recommended)".
- Keep artifacts mutually coherent: a change in `proposal.md` must be reflected in specs/design/tasks in the same pass.
- If the user means the `openspec update` CLI command (refresh generated files), run that command instead of this workflow.

### openspec-archive-change
- Archive only after the change is implemented; announce `Using change: <name>` first.
- `openspec instructions archive --change "<name>" --json` is advisory and optional — if it fails or the CLI is older, continue with no context/guidance and do not report an error.
- Treat returned `context` as required prompt input; treat `operationGuidance` as optional additive advice. Neither overrides built-in steps, user choices, resolved paths or CLI contracts — on conflict, report and keep the controlling value.
- Do not copy `context`/`operationGuidance` text verbatim into specs, artifacts, or the archive summary unless the user asks.
- Show only active (non-archived) changes when prompting; preserve each delta's full `<capability-path>`.
- Project check before the first write; never create the root as a side effect.

### active-orchestrator
- Thin orchestrator: route, never reimplement a phase. Dispatch in §4.2 order: `discovery-research` → `kb-creator` → `design-system` → `roadmap-generator` → `find-skill` → `skill-registry` → `agent-instruction`.
- Owns `.active-orchestrator-state.json` and **only** `version`, `step`, `owner`; each sub-skill writes its own section. `design-system` may raise a legacy version to 5 standalone.
- Never ask strategic content questions (system_type, scale, stack, problem, the 11-point checklist) — those belong to `kb-creator`/`discovery-research`. Asking *whether* to run Discovery is routing and is allowed.
- Hold a checkpoint at **every** phase boundary: never advance `step` without an explicit "Continuar". Standalone single-phase commands run that phase and stop.
- Resume by default when state exists with `step != "done"`; ask resume vs restart.
- Check sub-skill presence before dispatch → offer install → degrade gracefully if declined.
- `STOP` after every user question; never assume an answer.
- Never install anything autonomously; global installs are HIGH governance.
- Two "discovery" concepts: top-level `discovery` = product/market (optional, `discovery-research`); `kb.discovery` = architecture self-report (always present).

### design-taste-frontend-v1
- Baseline dials: `DESIGN_VARIANCE 8`, `MOTION_INTENSITY 6`, `VISUAL_DENSITY 4`; override only when the user explicitly asks.
- Verify dependencies in `package.json` before importing any library; if missing, output the install command. Never assume it exists.
- Tailwind for ~90% of styling; check whether the project is v3 or v4 before using version-specific syntax.
- **Emojis are banned** in code, markup, text and alt text — use icons (Phosphor/Radix) or clean SVG.
- Never `h-screen` — use `min-h-[100dvh]`. Use CSS Grid, never flexbox percentage math.
- Typography: `text-4xl md:text-6xl tracking-tighter leading-none` for display; body `text-base leading-relaxed max-w-[65ch]`. Serif is banned in dashboard/software UI.
- Color: max 1 accent, saturation < 80%, neutral base (Zinc/Slate). The "AI purple/blue" aesthetic is banned. One palette per project.
- Layout: centered hero banned at variance > 4; prefer split 50/50, left-aligned content, asymmetric whitespace. Any asymmetry must collapse to single column below `md`.
- Cards only when elevation communicates hierarchy; for dense dashboards use `border-t`, `divide-y`, negative space.
- Mandatory states: skeletal loading (not spinners), empty states, inline errors, `:active` tactile feedback (`scale-[0.98]`).
- Animate only `transform`/`opacity`; never `top/left/width/height`; no grain on scrolling containers; no arbitrary z-index spam.
- Forms: label above input, helper text in markup, error below, `gap-2` blocks.

### emil-design-eng
- Review UI code as a markdown table `| Before | After | Why |` — one row per issue. Never a Before/After list.
- Animation decision order: (1) does it animate at all? (2) what is the purpose? (3) which properties?
- Frequency rule: 100+/day → no animation ever; tens/day → remove or drastically reduce; occasional (modal, drawer, toast) → standard; rare/first-time → may add delight.
- **Never animate keyboard-initiated actions** — they must feel instant.
- Every animation needs a named purpose: spatial consistency, state indication, explanation, or feedback. No purpose → no animation.
- Never `transition: all`; name the exact properties and a short duration with `ease-out`-style curves (`ease-in` feels sluggish).
- Nothing appears from nothing: `scale(0)` → `scale(0.95)` + `opacity: 0`.
- Buttons need an `:active` state (`scale(0.97)`); popovers scale from their trigger via `transform-origin: var(--transform-origin)`; modals stay centered.
- Prefer CSS over JS for micro-interactions; avoid layout thrash and continuous JS-driven animation.
- Honor `prefers-reduced-motion`; unseen correctness beats visible cleverness.

### kb-creator

### find-skill
- Check the skills.sh leaderboard before a CLI search; then `npx skills find [query] [--owner <owner>]`.
- Never recommend from search results alone — verify installs (prefer 1K+, be wary <100), source reputation, and GitHub stars (<100 stars → skepticism).
- Present name, what it does, install count, source, install command and the skills.sh link.
- Install only after the user confirms: `npx skills add <owner/repo@skill> -g -y` (`-g` = global).
- If nothing fits, say so, offer to do the task directly, and suggest `npx skills init` for a custom skill.

### skill-creator
- Figure out where the user is in the loop (idea → draft → evals → iterate) and join there; flexibility over ceremony.
- Capture intent first: what it enables, when it triggers, expected output format, whether test cases are warranted (objective outputs yes, subjective outputs often not).
- Interview for edge cases, I/O formats, example files, success criteria, dependencies before writing test prompts.
- Loop: run test prompts with the skill → qualitative + quantitative eval (`eval-viewer/generate_review.py`) → rewrite from feedback → repeat → expand the test set.
- Finish with the description improver to optimize triggering.
- Match vocabulary to the user's level; define jargon when in doubt.

### web-scraper
- Output schema is fixed and non-negotiable: the 8 fields, same order, every time — that is what makes notes comparable.
- Never invent data the page does not show: use `(no publicado)` for missing fields.
- One URL → one note at `discovery/sources/<slug>.md` (slug from `scripts/slugify.py`, kebab-case, so re-runs overwrite instead of duplicating).
- Empty content / SPA shell / 403 / paywall / CAPTCHA → report the limitation in the field and continue; do not attempt evasion.
- No crawling, no mass scraping; only the pages explicitly provided. Process multiple URLs one by one and report resolved vs failed — one failure must not abort the batch.
- Read-only external skill: no approval gate needed per URL.
