## Compact Rules

Pre-digested rules per skill. Delegators copy matching blocks into sub-agent prompts as `## Project Standards (auto-resolved)`.

### fastapi-templates
- Layout: `api/v1/endpoints/`, `core/{config,security,database}.py`, `models/`, `schemas/`, `services/`, `repositories/`, `main.py`. In this repo the KB uses `app/core` + `app/modules` — follow the KB, not this skeleton verbatim.
- Handlers are `async def`; every DB call is awaited. Never call sync drivers inside an async handler.
- Session comes from a `Depends(get_db)` dependency; routers get sessions, services do not create them (this repo: router builds UoW, service opens it).
- Put shared concerns in `Depends` (auth, RBAC, pagination, DB session), never inline in the handler.
- `extra="forbid"` on all Pydantic v2 schemas (Create/Update/Read) — project rule.
- Driver URL: `postgresql+asyncpg://...`; `sqlalchemy[asyncio]` is required for the async engine.
- Dispose the engine in `lifespan` shutdown; never create an engine at import time per request.
- Tests: `pytest-asyncio` strict mode needs `@pytest_asyncio.fixture`; httpx 0.28+ requires `ASGITransport(app=app)` — `AsyncClient(app=...)` no longer exists.
- Override `get_db` via `app.dependency_overrides` and clear it after each test.

### auth-implementation-patterns
- Separate AuthN (who) from AuthZ (what). Validate **authorization on every request**, not just authentication.
- Hash passwords with bcrypt/argon2 and a cost from settings; never store or log plaintext.
- JWT access tokens are short-lived (15–30 min); `iat`/`exp` are numeric `NumericDate`.
- Cookie transport: `HttpOnly`, `SameSite=Lax`, bounded `Max-Age`, `Secure` per environment. Never return tokens in the JSON body, never read `Authorization` when the project contract says cookie-only.
- Rate-limit auth endpoints **before** credential verification; count by IP + identifier; answer `429` with `Retry-After`.
- Return identical message and comparable timing for "user exists" vs "user does not exist" (dummy hash) to prevent enumeration.
- RBAC: role check as a dependency (`require_rol`), not inside handlers; re-read current roles from the DB each request; deny by default; exempt only the documented public routes.
- Ownership checks are separate from role checks (`/mis-*` → 403 if not the owner).
- Log security events (login success/failure, role changes); never log secrets or tokens.

### postgresql-table-design
- `BIGINT GENERATED ALWAYS AS IDENTITY` for PKs; `UUID` only when opacity/global uniqueness is required.
- Money → `NUMERIC(p,s)`; timestamps → `TIMESTAMPTZ`; strings → `TEXT` (+`CHECK (length(...) <= n)`); ints → `BIGINT`; booleans → `BOOLEAN NOT NULL`.
- Never use `serial`, `timestamp` (no tz), `money`, `char(n)`/`varchar(n)`, or `timestamptz(0)`.
- **PostgreSQL does NOT auto-index FK columns.** Every FK referenced by queries gets an explicit index (project rule: index every FK).
- `NOT NULL` wherever semantically required; `CHECK` + `NOT NULL` together (`price NUMERIC NOT NULL CHECK (price > 0)`). NULL passes a `CHECK` — three-valued logic.
- `UNIQUE` allows multiple NULLs; use `UNIQUE NULLS NOT DISTINCT` (PG15+) when only one NULL is valid.
- Explicit `ON DELETE`/`ON UPDATE` on every FK.
- `CREATE TYPE ... AS ENUM` only for small stable sets; evolving values → `TEXT` + `CHECK`.
- Generated columns: `GENERATED ALWAYS AS (...) STORED` (used by this project for `items.precio_total`).
- Composite index → leftmost-prefix rule; most selective column first. Partial/expression/covering indexes before denormalizing.
- snake_case identifiers only; unquoted identifiers are lowercased, so mixed-case names silently break.
- Normalize to 3NF first; denormalize only for a measured read win.

### postgresql-optimization
- Always start with `EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)` on the real query — never guess.
- `pg_stat_statements` ordered by `total_time` to find the actual hot queries.
- Index choices: composite `(fk, sort_col)` for filtered+sorted lists; partial `WHERE status = 'active'` for hot subsets; expression `lower(email)` for case-insensitive lookups; covering `INCLUDE (...)` for index-only scans.
- Window functions (`SUM() OVER`, `DENSE_RANK()`, `LAG`) for per-entity running totals and rankings (reports, C-17/C-18) instead of N+1 queries.
- Pagination: `COUNT(*) OVER ()` or a separate filtered `count(*)` with **identical** `WHERE` — `total` must use the same filters as the page (RN-19).
- Avoid `OFFSET` on deep pages; prefer keyset pagination (`WHERE (created_at, id) < ($1, $2) ORDER BY created_at DESC, id DESC`) for large tables.
- Aggregate in the DB (`GROUP BY`, `jsonb_agg`, `array_agg`), not in Python.
- Watch `work_mem` / `shared_buffers` before blaming the query.
- JSONB: GIN index + `@>` containment, or extract to a generated B-tree column.
- Never build SQL by string concatenation; parameterize (`$1`, `$2`) — RN-15.

### python-design-patterns
- KISS: simplest thing that works. Complexity must be justified by a requirement.
- SRP: apply the "reason to change" test — if changes come from different domains (HTTP + business rules + formatting), split.
- Layers and dependency direction: API → Service → Repository. A service must never import from the API/handler layer.
- Inject dependencies through the constructor; 7+ constructor params means the class has too many responsibilities — split it, don't add a param bag.
- Composition over inheritance; keep composition 2–3 levels deep.
- Rule of three before abstracting; duplication that silently diverges is the exception — extract immediately, with a test.
- Functions 20–50 lines, one purpose. Explicit over clever. Delete dead code before reaching for a pattern.
- I/O at the edges; business logic pure so it is unit-testable without a DB.
- This repo: no `commit()` in repositories (only `flush()`); the UoW decides commit/rollback in `__aexit__` and does not close the session.

### python-testing-patterns
- AAA structure (Arrange/Act/Assert); one behaviour per test.
- Name: `test_<unit>_<scenario>_<expected>` — e.g. `test_terminar_orden_sin_stock_no_escribe_nada`.
- Tests are isolated: no shared mutable state, each test sets up its own data, cleanup via fixtures.
- Shared fixtures in `conftest.py`; split `tests/test_unit/`, `tests/test_integration/`, `tests/test_e2e/`.
- Async: `@pytest.mark.asyncio` + `@pytest_asyncio.fixture` (strict mode); api client via `httpx.AsyncClient(transport=ASGITransport(app))`.
- Override `app.dependency_overrides` for the DB/UoW and clear after; never hit the real DB from unit tests.
- Mock with `unittest.mock.Mock` + `side_effect` lists to assert retry counts; assert `call_count` explicitly.
- `freezegun` / `freeze_time` for token expiry and time-window logic (rate limiting, `password_cambiada_en`).
- Markers: `@pytest.mark.slow|integration|skipif|xfail`; run subsets with `-m`.
- Coverage: `pytest --cov=app --cov-fail-under=..`; meaningful coverage, not percentage theatre.
- Every regression test must fail before the fix and pass after.

### security-and-hardening
- Threat model first (5 minutes): map trust boundaries → name assets → STRIDE → write abuse cases as the first tests.
- Always: validate input at the boundary, parameterize queries, encode output, HTTPS, hash passwords, security headers, `HttpOnly`+`Secure`+`SameSite` cookies, native dependency audit against the committed lockfile.
- Never: commit secrets, log sensitive data, trust client-side validation, disable security headers, `eval()`/`innerHTML` with user data, store auth tokens in `localStorage`, leak stack traces.
- Authorization ≠ authentication: check the caller owns or is permitted on that specific object (IDOR/A01).
- CORS from an explicit origin list; never `*` with credentials.
- Strip sensitive fields before serializing (`password_hash`, reset tokens); generic error bodies, details to logs only.
- Rate limiting: strict on auth (this project: `LOGIN_MAX_INTENTOS`/`LOGIN_VENTANA_SEG` = 5/60s); in-memory counters multiply per instance — back with a shared store when >1 worker.
- Secrets via environment; `.env.example` committed with placeholders, real `.env*` gitignored. A leaked secret is compromised on landing → rotate first, then purge history.
- Ask-first actions: new auth flows, new PII categories, new integrations, CORS changes, uploads, rate-limit changes, role grants.
- Verification checklist before sign-off: audit clean, no secrets in history, input validated, authz on every route, headers present, no internal details in errors, rate limiting live.

### api-security-testing
- Requires: schema (OpenAPI/Postman/GraphQL introspection), **two credentials from different tenants**, low+high privilege tokens, example object IDs, out-of-scope routes, known rate limits. Never fabricate tokens or scan an API you do not own.
- Pass the spec as a target (`-t ./openapi.yaml`), not as prose in the instruction.
- Coverage checklist = OWASP API Top 10 (2023): BOLA/IDOR (API1), broken auth (API2), object property level authz — mass assignment + over-exposure (API3), unrestricted resource consumption (API4), broken function-level authz (API5).
- BOLA is only *proven* by reading tenant A's object with tenant B's token — an empty 200 is not a finding.
- For this project the high-value probes are: CLIENTE reading another client's orders/vehicles (`/mis-*`, 403 expected), MECANICO calling ADMIN-only routes, mass assignment on PATCH schemas (`extra=forbid` must reject), unbounded `size` in pagination.
- Every finding needs a working PoC request; replay it with `curl` before reporting.
- Do not run destructive admin/payment endpoints; keep tokens out of shell history and committed files.

- Derive a kebab-case change name from the request; ask only about ambiguity that materially affects scope/behaviour/compatibility/acceptance; assume-and-record the rest.

- Project check before the first write: `openspec list --json` → `root` object required. `"root": null` → offer `openspec init` only for an explicit OpenSpec request and wait.
- `Declared in` / `Invalid store declaration` errors mean an unresolvable store — stop and show `message` + `fix`, do not treat as uninitialized.
- Preserve an existing capability's full path; follow the project's established organization for new capabilities.

### openspec-apply-change
- Announce `Using change: <name>` and how to override before doing anything.

- `state: "all_done"` → congratulate and suggest archive; do not invent work.
- Implement tasks in order, edit only code (not planning artifacts), tick tasks as they complete.

- Never create the OpenSpec root as a side effect; treat `--store <id>` as sticky once selected.

### openspec-sync-specs
- Agent-driven merge: read delta specs and **edit the main specs directly** — do not copy whole files over.
- Main specs live at `<planningHome.root>/openspec/specs/` from `openspec status` — never a hardcoded repo path.
- Delta paths come **only** from `artifactPaths.specs.existingOutputPaths`. Missing/empty → report "no delta specs to sync" and stop; never infer them.
- Sync every path in `existingOutputPaths` unless the caller named an explicit subset — then sync only those and leave the rest untouched.
- Preserve the full `<capability-path>` from each delta when resolving its main spec.
- Sync ≠ archive: this leaves the change open on purpose.

### openspec-update-change
- Revises **existing** artifacts only; never creates missing ones and never edits code.
- Missing artifact → `openspec status --change "<name>" --json` names the next one and `openspec instructions "<artifact-id>" --change "<name>" --json` explains how to write it.
- When prompting for a change, list the top 3–4 most recently modified with status and `lastModified`, marking the most recent "(Recommended)".
- Keep artifacts mutually coherent: a change in `proposal.md` must be reflected in specs/design/tasks in the same pass.
- If the user means the `openspec update` CLI command (refresh generated files), run that command instead of this workflow.

### openspec-archive-change

### design-taste-frontend-v1
- Baseline dials: `DESIGN_VARIANCE 8`, `MOTION_INTENSITY 6`, `VISUAL_DENSITY 4`; override only when the user explicitly asks.
- Verify dependencies in `package.json` before importing any library; if missing, output the install command. Never assume it exists.
- Tailwind for ~90% of styling; check whether the project is v3 or v4 before using version-specific syntax.
- **Emojis are banned** in code, markup, text and alt text — use icons (Phosphor/Radix) or clean SVG.
- Never `h-screen` — use `min-h-[100dvh]`. Use CSS Grid, never flexbox percentage math.
- Typography: `text-4xl md:text-6xl tracking-tighter leading-none` for display; body `text-base leading-relaxed max-w-[65ch]`. Serif is banned in dashboard/software UI.
- Color: max 1 accent, saturation < 80%, neutral base (Zinc/Slate). The "AI purple/blue" aesthetic is banned. One palette per project.
- Layout: centered hero banned at variance > 4; prefer split 50/50, left-aligned content, asymmetric whitespace. Any asymmetry must collapse to single column below `md`.
- Cards only when elevation communicates hierarchy; for dense dashboards use `border-t`, `divide-y`, negative space.
- Mandatory states: skeletal loading (not spinners), empty states, inline errors, `:active` tactile feedback (`scale-[0.98]`).
- Animate only `transform`/`opacity`; never `top/left/width/height`; no grain on scrolling containers; no arbitrary z-index spam.
- Forms: label above input, helper text in markup, error below, `gap-2` blocks.

### emil-design-eng
- Review UI code as a markdown table `| Before | After | Why |` — one row per issue. Never a Before/After list.
- Animation decision order: (1) does it animate at all? (2) what is the purpose? (3) which properties?
- Frequency rule: 100+/day → no animation ever; tens/day → remove or drastically reduce; occasional (modal, drawer, toast) → standard; rare/first-time → may add delight.
- **Never animate keyboard-initiated actions** — they must feel instant.
- Every animation needs a named purpose: spatial consistency, state indication, explanation, or feedback. No purpose → no animation.
- Never `transition: all`; name the exact properties and a short duration with `ease-out`-style curves (`ease-in` feels sluggish).
- Nothing appears from nothing: `scale(0)` → `scale(0.95)` + `opacity: 0`.
- Buttons need an `:active` state (`scale(0.97)`); popovers scale from their trigger via `transform-origin: var(--transform-origin)`; modals stay centered.
- Prefer CSS over JS for micro-interactions; avoid layout thrash and continuous JS-driven animation.
- Honor `prefers-reduced-motion`; unseen correctness beats visible cleverness.

### discovery-research
- Runs **before** the KB; output (`discovery/discovery.md` + `state.discovery`) is input for `kb-creator`, never a replacement.
- Workflow: sources (competitors/docs — invoke `web-scraper` once per URL) → 11-point checklist Q&A → final gate → write.
- Governance MEDIA: never write `discovery/discovery.md` or touch the state file before the user confirms the summary.
- If scraping already answered a checklist point (e.g. competitors), present it as a summary to confirm — do not re-ask.
- Missing URLs is not a blocker: continue with Q&A only and say scraping did not run.
- After scraping, run `scripts/collect_sources.py` to build the comparison table before the Q&A.
- Risks/open questions come from unverified assumptions — mark what is a fact vs an assumption.
- Reject vague answers (see the anti-pattern table in `references/checklist.md`); ask 3–5 questions per round with a/b/c options and "why it matters".
- Writes only the `discovery` section of the state file; never `version`, `step`, `owner`, or other phases' sections.

### kb-creator
- Output goes to `knowledge-base/` at the project root; **never** mix with `docs/` (source documents).
- The 10 canonical files are mandatory with exact names: `01_vision_y_objetivos`, `02_descripcion_general`, `03_actores_y_roles`, `04_modelo_de_datos`, `05_reglas_de_negocio`, `06_funcionalidades`, `07_flujos_principales`, `08_arquitectura_propuesta`, `09_decisiones_y_supuestos`, `10_preguntas_abiertas` + `README.md`.
- Business rules get stable codes (`RN-XX`), actors get an RBAC table, entities get an ERD — that structure is what the roadmap/changes consume.
- Mode A (silent, `docs/` has sources): read everything, write the KB, **ask no questions**; record ambiguities in `10_preguntas_abiertas.md`; never invent a `discovery` value.
- Mode B (interactive): analyst + PM partner — summarize, list 3–5 uncertainties, propose 2–3 approaches with pros/cons, ask 3–5 strategic questions, wait, then write file by file with validation.
- Optional extras use prefix `1X_`/`2X_` kebab-case; extras never replace a canonical file.
- Mode → `state.kb.source`: Mode A = `"ingest"`, Mode B = `"interactive"`; a run that started from `docs/` is `"ingest"` even if gaps were filled by questions.
- State hook writes **only** `state.kb` (never `step`, `owner`, `roadmap`, `skills`, `agents`) and only if `.active-orchestrator-state.json` already exists.
- Close with a summary table `file → lines → topics covered`.

### roadmap-generator
- Pre-checks: `knowledge-base/` exists, contains the 10 canonical files, and `openspec/` exists. Any failure → generate nothing and say which command to run.
- Output is a single root-level `CHANGES.md` (never inside `openspec/`) — it is the master index of the repo.
- Always read `04_modelo_de_datos.md`, `06_funcionalidades.md`, `07_flujos_principales.md`, `08_arquitectura_propuesta.md`; optionally `03`, `05`, `10`.
- Orchestrated input: use `state.kb.files` as the authoritative path list and `state.kb.discovery` as a naming/governance hint only (files remain the source of truth).
- Contract sections, do not add or remove: how-to, dependency tree (ASCII), parallelism gates, critical path, 3-agent plan, then `## FASE N` blocks with `### [C-NN] name` + Estado/Scope/Dependencias/Governance/Leer antes.
- Dependency hierarchy: infra first (C-01 foundation, no deps) → core models (C-02) → auth before protected resources → referenced entity before referencing → backend before coupled frontend → external integrations last → dashboards last → visual refactors last of all.
- Governance: BAJO = scaffolding/CRUD/simple pages; MEDIO = stateful flows; ALTO = notifications, roles, gateways, observability; CRITICO = auth, payments, security data, audit trail, core models everything references.
- Scope bullets must be operational (endpoint, model, numbered migration, event, expected tests) — never "implementar el sistema de X".
- "Leer antes": 3–5 KB files per change with section pointers.
- Fire-and-forget: no questions. State hook writes only `state.roadmap` (`created_by`, `source`, `changes[]`).

### find-skill
- Check the skills.sh leaderboard before a CLI search; then `npx skills find [query] [--owner <owner>]`.
- Never recommend from search results alone — verify installs (prefer 1K+, be wary <100), source reputation, and GitHub stars (<100 stars → skepticism).
- Present name, what it does, install count, source, install command and the skills.sh link.
- Install only after the user confirms: `npx skills add <owner/repo@skill> -g -y` (`-g` = global).
- If nothing fits, say so, offer to do the task directly, and suggest `npx skills init` for a custom skill.

### skill-creator
- Figure out where the user is in the loop (idea → draft → evals → iterate) and join there; flexibility over ceremony.
- Capture intent first: what it enables, when it triggers, expected output format, whether test cases are warranted (objective outputs yes, subjective outputs often not).
- Interview for edge cases, I/O formats, example files, success criteria, dependencies before writing test prompts.
- Loop: run test prompts with the skill → qualitative + quantitative eval (`eval-viewer/generate_review.py`) → rewrite from feedback → repeat → expand the test set.
- Finish with the description improver to optimize triggering.
- Match vocabulary to the user's level; define jargon when in doubt.

### web-scraper
- Output schema is fixed and non-negotiable: the 8 fields, same order, every time — that is what makes notes comparable.
- Never invent data the page does not show: use `(no publicado)` for missing fields.
- One URL → one note at `discovery/sources/<slug>.md` (slug from `scripts/slugify.py`, kebab-case, so re-runs overwrite instead of duplicating).
- Empty content / SPA shell / 403 / paywall / CAPTCHA → report the limitation in the field and continue; do not attempt evasion.
- No crawling, no mass scraping; only the pages explicitly provided. Process multiple URLs one by one and report resolved vs failed — one failure must not abort the batch.
- Read-only external skill: no approval gate needed per URL.

### skill-registry
- Scans project skill dirs (`.claude/`, `.gemini/`, `.agent/`, `skills/`, plus `.agents/`/`.opencode/`) and user-level dirs; dedupes with project-level winning.
- Skips `sdd-*`, `_shared`, and itself.
- **The compact rules are the product**: 5–15 actionable lines per skill, no purpose/motivation, no full code examples — they are pasted into sub-agent prompts.
- Always writes `.atl/skill-registry.md`; upserts to engram with `topic_key` when available; adds `.atl/` to `.gitignore` if that file exists.
- Sub-agents never read the registry themselves — the delegator resolves and injects.
